# ซ่อมข้อความ resume เพื่อ "ค้นหา" เท่านั้น — ไม่แก้ข้อความที่ HR อ่าน

PDF ไม่ได้เก็บข้อความเป็นบรรทัด pdf.js คืนมาเป็นชิ้น ๆ (text item) ตามรอยต่อฟอนต์/เคิร์นนิ่ง
อีเมลใบเดียวจึงออกมาได้เป็น `["somchai.j", "@gmail.com"]` หรือถูกตัดคนละบรรทัด ผลคือ resume
ที่มีอีเมลชัดเจนแต่ระบบหาไม่เจอ (เจอจริง 2 ใน 3 ใบ)

การหาอีเมล/ชื่อจึงทำบน **สำเนาที่ซ่อมแล้ว** — ปิดช่องว่างรอบ `@` ต่อบรรทัดที่ถูกตัดกลางอีเมล
คลายรูปแบบกันสแปม `(at)` `(dot)` — ส่วน `resumeText` ที่บันทึกลง DB และแสดงให้ HR อ่าน
ยังเป็นข้อความดิบจากไฟล์เสมอ

เหตุผล: ข้อความที่ HR เห็นคือหลักฐานว่าไฟล์เขียนว่าอะไรจริง ๆ ใช้ตัดสินใจและใช้ยืนยันตอนคะแนน
match ดูผิดปกติ ถ้าเขียนทับด้วยข้อความที่ระบบ "เดา" ว่าถูก จะแยกไม่ออกว่าอะไรมาจากผู้สมัคร
อะไรมาจากตัวซ่อม และการไฮไลต์ทักษะจะชี้ไปยังตำแหน่งที่ไม่มีอยู่จริงในไฟล์

ด้วยเหตุผลเดียวกัน การค้นอีเมลทำสองชั้น: หาแบบเข้ม (ไม่ยอมให้มีช่องว่าง) ก่อนเสมอ
ถ้าไม่เจอจึงค่อยหาแบบผ่อนปรนบนสำเนาที่ซ่อม — ไฟล์ที่ปกติดีอยู่แล้วจึงให้ผลเท่าเดิมทุกประการ
ความเสี่ยงที่ตัวซ่อมจะเดาเพี้ยนถูกจำกัดไว้เฉพาะไฟล์ที่ไม่มีทางหาเจอด้วยวิธีปกติอยู่แล้ว
