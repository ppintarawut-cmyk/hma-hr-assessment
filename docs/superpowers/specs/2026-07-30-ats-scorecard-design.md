# ATS Scorecard — Design

วันที่: 2026-07-30
ไฟล์ที่แก้: `hma-ats.html` (ไฟล์เดียว)

## ปัญหา

หลังสัมภาษณ์ผู้สมัคร ไม่มีที่บันทึกผลประเมินอย่างมีโครงสร้าง คะแนนที่ระบบมีอยู่ (`c.score`)
เป็นคะแนน match ระหว่าง resume กับตำแหน่ง ซึ่งบอกอะไรเกี่ยวกับตัวคนไม่ได้เลย
การเปรียบเทียบผู้สมัครหลายคนจึงต้องอาศัยความจำ

## ขอบเขต

**ทำ**
- บันทึกผลสัมภาษณ์แบบให้คะแนนรายหัวข้อ หลายรอบต่อผู้สมัครหนึ่งคน
- ตั้งค่าหัวข้อประเมินและน้ำหนักได้
- แสดงคะแนนสัมภาษณ์รอบล่าสุดในตารางผู้สมัครและการ์ด Kanban
- เพิ่มคะแนนสัมภาษณ์ใน CSV export

**ไม่ทำ**
- ไม่มีสรุปชี้ขาด จ้าง/ไม่จ้าง (คะแนนตัวเลขพอ — คำตัดสินอยู่ในหัวคนสัมภาษณ์)
- ไม่เรียงลำดับ/กรองด้วยคะแนนสัมภาษณ์
- ไม่มีหลายผู้ประเมิน ไม่มี sync — ผู้ใช้คนเดียว local-first ตาม `docs/decisions/0001`
- ไม่แตะ `c.score` (คะแนน match resume) เดิม

## ข้อจำกัดที่ยึด

- **decision 0001** — local-first, ผู้ใช้คนเดียว, ห้ามเพิ่ม backend
- **decision 0004** — retention 2 ปีนับจากเคสปิด: scorecard อยู่บน record ผู้สมัคร จึงถูกลบไปพร้อมกันเอง ไม่ต้องทำกลไกแยก
- **quota localStorage ~5MB** — โค้ดเดิมถึงขั้นยอมไม่เก็บ `sections` ซ้ำเพื่อประหยัด scorecard ~200 bytes/ใบ เทียบกับ `resumeText` หลาย KB จึงไม่กระทบ
- **`makeCandidate()` เป็น constructor เดียว** ของ record ผู้สมัครทุกช่องทาง (คอมเมนต์ในโค้ดกำชับไว้) — field ใหม่ต้องเพิ่มผ่านที่นี่

## โครงสร้างข้อมูล

### เกณฑ์กลาง — `DB.scorecardCriteria`

เก็บใน `DB` ข้างๆ `emailTemplates` ล้อ pattern เดิมรวมถึง migration guard ใน `loadDB()`
(`if (!Array.isArray(d.scorecardCriteria) || !d.scorecardCriteria.length) d.scorecardCriteria = seedScorecardCriteria();`)

```js
[
  { id:'c1', label:'ความรู้ทางเทคนิค / ตรงสายงาน', weight:3 },
  { id:'c2', label:'การสื่อสาร',                    weight:2 },
  { id:'c3', label:'ทัศนคติ & ความรับผิดชอบ',        weight:2 },
  { id:'c4', label:'ความเหมาะสมกับทีม',              weight:2 },
  { id:'c5', label:'การแก้ปัญหา',                   weight:1 },
]
```

ชุดเดียวใช้ทุกตำแหน่ง น้ำหนัก 1–5

### ใบประเมิน — `candidate.scorecards`

array บน record ผู้สมัคร เรียงตามลำดับที่เพิ่ม (แสดงผลกลับด้าน ใหม่→เก่า)

```js
[{
  id: 'sc…',
  round: 'สัมภาษณ์ HR',
  at: '2026-07-30T09:12:00.000Z',
  ratings: { c1:4, c2:5, c3:3, c4:4, c5:3 },   // หัวข้อที่กด "—" จะไม่มี key
  note: 'สื่อสารดี ประสบการณ์ตรงสายยังน้อย',
  total: 78,
  weightsUsed: [                                // snapshot เต็ม ณ เวลาบันทึก
    { id:'c1', label:'ความรู้ทางเทคนิค / ตรงสายงาน', weight:3 },
    …
  ]
}]
```

### ทำไม `total` และ `weightsUsed` ถึง freeze

ผู้ใช้แก้หัวข้อ/น้ำหนักได้ทีหลัง ถ้าคำนวณสดทุกครั้ง คะแนนของรอบที่ประเมินไปแล้วจะขยับเอง
ย้อนหลังเมื่อเปลี่ยนน้ำหนัก ซึ่งผิด — บันทึกการประเมินต้องนิ่ง

`weightsUsed` เก็บ **snapshot เต็มรวม label** ไม่ใช่แค่น้ำหนัก เพื่อให้ใบเก่ากางดูย้อนหลังได้เสมอ
แม้หัวข้อนั้นจะถูกลบออกจากเกณฑ์ปัจจุบันไปแล้ว — ใบประเมินต้องอ่านได้ด้วยตัวเอง
โดยไม่ต้องพึ่งสถานะปัจจุบันของระบบ

### สูตร

```
total = round( Σ(rating × weight) / Σ(5 × weight) × 100 )
```

คิดเฉพาะหัวข้อที่ให้คะแนน — หัวข้อที่กด "—" ถูกตัดออกจาก **ทั้งเศษและส่วน**
กรอกไม่ครบจึงยังได้คะแนนที่ยุติธรรม ไม่ถูกลงโทษเหมือนได้ 0

normalize เป็น 0–100 เพื่อให้เทียบสายตากับคะแนน match ได้และใช้ `scoreBar()`/`scoreClass()` เดิมซ้ำ

ตัวอย่าง: ratings 4/5/3/4/3 กับ weights 3/2/2/2/1
→ Σ(r×w) = 12+10+6+8+3 = 39 · Σ(5×w) = 50 · 39/50 = **78**

## UI

เลือกวางไว้ในโมดัลรายละเอียดผู้สมัคร (ไม่ใช่แท็บใหม่หรือโมดัลแยก) เพราะจังหวะใช้งานจริงคือ
"สัมภาษณ์เสร็จ → เปิดโปรไฟล์คนนั้น → ให้คะแนน" และต้องมองเห็น resume + ผลสอบไปด้วยขณะให้คะแนน

### ส่วน "ผลสัมภาษณ์" ใน `detailHTML()`

วาง**ต่อจาก `cloudSection`** (ผลสอบจาก Firestore) และ**ก่อนส่วน resume ฉบับเต็ม**
— รวมของที่เป็นผลประเมินไว้ด้วยกัน (match → ผลสอบ → สัมภาษณ์) แล้วค่อยตามด้วยข้อมูลดิบยาวๆ

**พับเป็นค่าเริ่มต้น** เพราะโมดัลนี้ยาวอยู่แล้ว จำสถานะพับ/กางใน localStorage
ล้อ `hma_ats_candview` (คีย์ใหม่: `hma_ats_sc_open`)

- มีใบแล้ว: `🗣 ผลสัมภาษณ์ — 78 · 2 รอบ ▸`
- ยังไม่มี: `🗣 ผลสัมภาษณ์ — ยังไม่ได้ประเมิน ▸` พร้อมปุ่มเพิ่มรอบตรงนั้นเลย

**เมื่อกาง** — รายการใบ ใหม่→เก่า ใบละแถว: ชื่อรอบ · วันที่ · คะแนน (`scoreBar()`) · [แก้ไข] [ลบ]
พร้อมบันทึกย่อบรรทัดล่าง กดที่แถวเพื่อกางดูคะแนนรายหัวข้อ (เรนเดอร์จาก `weightsUsed` ของใบนั้น)

ล่างสุด: `＋ เพิ่มรอบสัมภาษณ์` และลิงก์ `⚙ ตั้งค่าหัวข้อประเมิน`

### ฟอร์มให้คะแนน — inline ไม่ใช่โมดัลซ้อน

กางออกในที่ ไม่เปิดหน้าต่างใหม่ เพราะโมดัลซ้อนจะบัง resume/ผลสอบ ซึ่งเป็นเหตุผลที่เลือกวางไว้ตรงนี้ตั้งแต่แรก

- **ชื่อรอบ** — input + `<datalist>` เสนอ "สัมภาษณ์ HR / สัมภาษณ์หัวหน้างาน / สัมภาษณ์ผู้บริหาร" พิมพ์เองได้
- **แต่ละหัวข้อ** — ปุ่ม 1–5 แบบ segmented (คลิกเดียวจบ) + ป้ายน้ำหนัก `×3` ข้างชื่อหัวข้อ
- **ปุ่ม "—"** ต่อหัวข้อ = ไม่ประเมินหัวข้อนี้
- **บันทึกย่อ** — textarea
- **คะแนนรวมสด** อัปเดตทุกครั้งที่กด
- ปุ่ม บันทึก / ยกเลิก

"แก้ไข" ใช้ฟอร์มเดียวกัน prefill ค่าเดิม — ฟอร์มเดียวสองหน้าที่

### โมดัลตั้งค่าหัวข้อ

โมดัลแยก ล้อ `openTplManager()` (จัดการเทมเพลตอีเมล) — โค้ดเดิมเปิดโมดัลซ้อนจากในโมดัลรายละเอียดอยู่แล้ว
(`openEmailDraft` ในปุ่มของ `detailHTML`) จึงเป็น pattern ที่โปรเจกต์นี้ใช้อยู่

ตารางหัวข้อ: ชื่อ · น้ำหนัก 1–5 · ปุ่มลบ · ปุ่มเพิ่มหัวข้อ · ปุ่มคืนค่าเริ่มต้น

ต้องมีข้อความเตือนในโมดัลว่า **"มีผลกับใบที่ประเมินหลังจากนี้เท่านั้น"**
ไม่งั้นผู้ใช้จะงงว่าทำไมแก้น้ำหนักแล้วคะแนนเก่าไม่ขยับ

### ตารางผู้สมัคร

เพิ่มคอลัมน์ **"สัมภาษณ์"** ถัดจากคอลัมน์คะแนน match ใช้ `scoreBar()` เดิม

- ยังไม่ประเมิน → **`—` สีเทา ไม่ใช่ 0** (0 อ่านว่า "สัมภาษณ์แล้วได้ศูนย์" คนละความหมาย จะทำให้ตัดสินใจผิด)
- หลายรอบ → เลขรอบล่าสุด + จำนวนรอบกำกับ `85 ·2` กันเข้าใจผิดว่ามีคะแนนเดียว

### การ์ด Kanban

`kc-foot` เพิ่มชิปคะแนนสัมภาษณ์เล็กๆ ข้างคะแนน match นำหน้าด้วย 🗣
พื้นที่จำกัด — โชว์แค่ตัวเลข ไม่มีแถบ

### CSV export

`exportCSV()` เพิ่ม 2 คอลัมน์: `Interview Score`, `Interview Rounds`
(ยังไม่ประเมิน → ว่าง ไม่ใช่ 0)

แทรกใน `head` ต่อจาก `'Match Score'` และใน `row` ต่อจาก `c.score` เพื่อให้คะแนนสองตัวอยู่ติดกัน
ต้องแทรก**ก่อน**ส่วนที่ต่อท้ายด้วยคอลัมน์ผลสอบแบบ dynamic (`codes.forEach`) ไม่งั้นหัวตารางกับข้อมูลจะเหลื่อมกัน

หมายเหตุ: `exportCSV()` export เฉพาะแถวที่ตรง filter ที่เปิดอยู่ (`filteredCandidates()`)
พฤติกรรมนี้คงเดิม ไม่แตะ

## Edge case

| กรณี | พฤติกรรม |
|---|---|
| record เก่าไม่มี field `scorecards` | `(c.scorecards \|\| [])` ทุกจุด ล้อสไตล์ป้องกันเดิม (`(c.matched \|\| [])`) ไม่ต้องเขียน migration |
| ลบหัวข้อที่ใบเก่าอ้างอยู่ | ใบเก่ากางดูได้ครบ เพราะ `weightsUsed` snapshot รวม label |
| แก้น้ำหนักหลังบันทึกใบแล้ว | คะแนนใบเก่านิ่ง ไม่ขยับ |
| กด "—" ทุกหัวข้อ | บันทึกไม่ได้ + ข้อความบอกเหตุผล (ไม่มีอะไรให้คำนวณ) |
| ลบใบ scorecard | `confirm()` ก่อน ตามที่โค้ดใช้อยู่ |
| ลบผู้สมัคร | scorecard หายตามเอง (อยู่บน record) |
| auto-backup ลงไฟล์ | ไม่ต้องแตะ `saveDB()` เขียน `DB` ทั้งก้อนอยู่แล้ว |
| localStorage เต็มตอนบันทึก | `saveDB()` มี try/catch + toast เตือนอยู่แล้ว ไม่ต้องเพิ่ม |

## แผนเทสต์

`test_scorecard.py` — patchright + Chrome headless ตามชุดเดิมของโปรเจกต์
(ต้อง `python -m http.server 8791` ในโฟลเดอร์ `files` ก่อน)

1. คำนวณถูก — 4/5/3/4/3 กับน้ำหนัก 3/2/2/2/1 → **78**
2. กด "—" บางหัวข้อ → ตัดจากทั้งเศษและส่วน ไม่นับเป็น 0
3. บันทึกแล้วเลขขึ้นในตาราง **และ** การ์ด Kanban ตรงกัน
4. เพิ่มรอบที่ 2 → ตารางโชว์รอบล่าสุด ไม่ใช่ค่าเฉลี่ย
5. record ที่ไม่มี `scorecards` → ขึ้น `—` ไม่ throw
6. แก้น้ำหนักในโมดัลตั้งค่า → คะแนนใบเก่า **ไม่ขยับ**
7. ลบหัวข้อ → กางใบเก่ายังเห็นชื่อหัวข้อเดิม
8. reload → ข้อมูลอยู่ครบ
9. CSV export มี 2 คอลัมน์ใหม่ ค่าตรงกับที่แสดงบนจอ

ข้อ 6 และ 7 คือหัวใจ — พังง่ายที่สุดถ้า implement ผิด

## ผลกระทบต่อไฟล์

ทั้งหมดอยู่ใน `hma-ats.html`:

- `loadDB()` — migration guard สำหรับ `scorecardCriteria`
- `seedScorecardCriteria()` — ใหม่
- `makeCandidate()` — เพิ่ม `scorecards: []`
- `calcScorecardTotal()`, `latestScorecard()` — ใหม่
- `detailHTML()` — แทรกส่วนผลสัมภาษณ์
- `scorecardSectionHTML()`, `scorecardFormHTML()`, `saveScorecard()`, `deleteScorecard()` — ใหม่
- `openCriteriaManager()` + โมดัลใหม่ใน markup — ใหม่
- `renderCandTable()` — คอลัมน์ใหม่ + header
- `candCardHTML()` — ชิปใหม่
- `exportCSV()` — 2 คอลัมน์ใหม่ (แทรกก่อนคอลัมน์ผลสอบแบบ dynamic)
- CSS — segmented rating buttons, ชิปคะแนนสัมภาษณ์
